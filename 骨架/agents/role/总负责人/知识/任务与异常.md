# 任务与异常

总负责人怎么选任务类型、登记、交接、处理异常和维护项目。阶段和检查的机器定义在 `agents/role/总负责人/工具/任务管理/流程定义.json`，命令见同目录的 README；所有智能体共用的做法见 `agents/公共/规则.md`。

## 1. 任务类型

| 本人要的 | 任务类型 | 谁来做 | 终点 |
|---|---|---|---|
| 刚部署的新项目开工 | 不登记 | 总负责人按 `agents/role/总负责人/知识/开工.md` | 回答写进账号档案，定位确认后 stage 改成"已开工" |
| 已有账号转型、停更重启 | research | 总负责人按 `agents/role/总负责人/知识/转型与重启.md`，诊断派增长分析 | 保留／放弃经本人确认，方向和路径确认后写回 |
| 建立或调整定位，研究对标 | research | 总负责人按 `agents/role/总负责人/知识/定位与对标.md`，取证派市场研究 | 有依据的方案、本人确认和验证计划；之后才出内容策略和选题 |
| 做一条视频、完整内容包 | content | 团队，按总负责人说明书的"做内容" | 完整内容包，本人验收 |
| 给已有作品做封面、标题、正文、标签 | delivery | 后期，再派审片 | 指定的文字或封面，或完整内容包 |
| 分析已发布内容 | research | 增长分析 | 真实数据、结论边界和经验更新 |
| 项目维护 | maintenance | 总负责人，按第 7 节 | 改完并通过检查 |

图文等还没单列的内容也走 content，用对应技能，不硬套视频的做法。混合视频选一条主制作路线，再借另一条的必要步骤，不重复登记同一项工作。

## 2. 开始每个任务

1. **定范围。** 明确本人要求、已有材料、终点和不确定项；只问会实质改变方案的缺项（做内容阶段按说明书"什么时候找本人"）。讨论、总结、审查停在对应范围，不默认变成制作。
2. **查重与接续。** 查任务总览和对应 task.json，做内容加查选题池和必要的账号数据；已有任务就接续，没有再用任务工具创建。
3. **登记。** 本人的要求用 `authorize` 登记原话；用到的知识文件路径用 `update --input` 登记；每次交接在 next_action 写当前步骤、有效文件和恢复条件。

## 3. 阶段与检查

| 任务类型 | 机器阶段 | 卡住的检查或确认 | 本人验收 |
|---|---|---|---|
| content | 调研 → 创意 → 评审 → 方案 → 制作 → 合成 → 审片 → 交付 | "创意评审"通过才能进方案；"成片审查"通过才能进交付 | 需要 |
| delivery | 理解作品 → 包装方案 → 制作材料 → 检查 → 交付 | 没有 | 需要 |
| research | 问题 → 取证 → 分析 → 沉淀 | 要改定位时加 positioning 确认（放在沉淀前）；转型加 direction 确认（放在分析前） | 不需要 |
| maintenance | 查现状 → 方案 → 执行 → 检查 → 沉淀 | 涉及权限、自动执行范围、删除时按授权确认 | 不需要 |

- 检查结论用 `check` 登记，passed 必须附产物文件；名称用"创意评审""成片审查"。
- 确认只登记本人真实原话，绑定具体文件版本；文件改了确认就失效。核心方案改了，受影响的确认改为待定，没变的部分不重复问。
- 交付先 `check-package`，整份复制到 `交付/` 的全新目录后用 `delivery` 登记；本人验收用 `accept`。发布不是结束条件。
- 验收不通过就在原任务内修订，新交付重新等验收。发布数据到齐后另建复盘任务，不把制作任务挂着等发布。
- 本人直接指定的选题按原话登记；本人只要一个提示词等窄成果时按明确范围交付。

## 4. 交接记录

每次交接只记必要信息，可以并入现有简报、报告或任务记录，不为此建空文件。

| 项目 | 写什么 |
|---|---|
| 目标与范围 | 任务 ID、请求终点、已授权的操作 |
| 决定与确认 | 锁定的决定、本人来源、确认的文件和版本；没确认就写待确认 |
| 实际产物 | 当前有效文件，原片、工程、成品的关系，相对项目根目录的路径 |
| 技能与工具 | 实际用的技能和必要子项、工具与版本、关键方法 |
| 证据与限制 | 检查方法、结果、证据位置；来源和许可条件；未验证范围 |
| 下一步 | 要处理的事、在等谁或什么条件 |

## 5. 派工失败和返工

- 子智能体没交产物、产物校验不过或明显跑题：带着问题重派一次；还不行就换做法或缩小范围，写进 issues。
- 返工只派回负责的智能体，附审片报告或评审意见里对应的条目；同一问题到 rework_rounds_max 轮还不过，停下来找本人。
- 子智能体之间意见冲突时按证据裁决，理由写进任务目录。

## 6. 异常处理

| 情况 | 现在做什么 | 什么时候恢复 |
|---|---|---|
| 缺目标、关键材料或必要授权 | 记录缺项；开工阶段问本人，做内容阶段只在说明书列的情况下问，先做不依赖它的工作 | 收到必要信息或明确授权 |
| 确认后的核心方案变了 | 受影响的确认改为待定，回到对应步骤 | 新方案确认；没变的部分不重复确认 |
| 外部提交结果不明 | 保存请求、回包和 ID，停止重提 | 查清原任务状态，按工具规则恢复 |
| 产物不合格 | 记录时间码和具体缺陷，派回负责的智能体，选成本合理的修法 | 受影响部分重查通过 |
| 缺播放、试听或数据能力 | 保留能证实的部分，标未验证 | 有了检查能力，或本人明确接受这个限制 |
| 版本或目录冲突 | 重新读取记录，选新的交付名称，不覆盖 | 当前版本和目标目录核对通过 |
| 请求已完成 | 更新任务和必要记录，简洁交付后停止 | 本人提出新的明确请求 |

## 7. 项目维护

1. 查现状：读最小必要的文件和引用，确认已有工作和目录权限，写清影响范围和完成条件。
2. 方案：列出要改的文件、理由和验证方法；涉及权限、自动执行范围、删除时按已有授权判断是否要确认。
3. 执行：在范围内修改，写前重读；不改无关工程、受保护目录或共享技能源。改了某个子智能体的 `agent.yaml`，运行 `python3 agents/公共/工具/团队/生成角色.py`。
4. 检查：运行 `python3 agents/公共/工具/项目检查/检查.py`；程序改动另测真实行为，失败先诊断，不重复无效检查。
5. 沉淀：更新对应的账号档案、说明书、索引和当天日志，登记结束和剩余限制。

项目升级先在本项目验证，再考虑通用提炼；不顺手安装技能、调度器、后台服务或创建其他项目。维护任务内部检查通过就可以结束，但不代表本人验收了主观体验；本人要求先验收时，登记确认条件并等待。
